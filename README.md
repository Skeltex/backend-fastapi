# backend-fastapi

REST API блога на FastAPI: пользователи, категории, местоположения, публикации и комментарии. Проект перенесен с Django, данные хранятся в PostgreSQL.

## Локальный запуск

Нужны Python 3.14, [uv](https://docs.astral.sh/uv/) и Docker для PostgreSQL.

1. Скопируйте `.env.example` в `.env` и задайте `SECRET_KEY` и `POSTGRES_PASSWORD`. Для `HS256` ключ должен быть не короче 32 байт, для `HS384` не короче 48, для `HS512` не короче 64. Сгенерировать ключ и пароль можно так:

   ```bash
   python -c "import secrets; print(secrets.token_urlsafe(64))"
   ```

2. Запустите PostgreSQL:

   ```bash
   docker compose up -d db
   ```

   Порт базы открывается только на `127.0.0.1`. Если порт 5432 уже занят, например локально установленным PostgreSQL, укажите в `.env` другой, например `POSTGRES_PORT=5433`. Чтобы работать с другим сервером PostgreSQL, пропустите этот шаг и задайте `POSTGRES_HOST`, `POSTGRES_PORT` и учетные данные или `DATABASE_URL`.

3. Установите зависимости и примените миграции:

   ```bash
   uv sync
   uv run alembic upgrade head
   ```

4. Запустите сервер:

   ```bash
   uv run fastapi dev main.py
   ```

API доступно по адресу http://localhost:8000/api/v1, документация по адресу http://localhost:8000/docs.

Если папку проекта переносили или переименовывали, пересоздайте окружение командой `uv venv --clear && uv sync`: скрипты в `.venv` хранят абсолютные пути.

## Docker

```bash
docker compose up
```

Поднимаются два контейнера: PostgreSQL (`db`) и приложение (`api`). Перед запуском нужен файл `.env` из шага 1. Образ приложения пересобирается при каждом `docker compose up`, поэтому контейнер всегда запускается с текущим кодом. Приложение дожидается готовности базы и применяет миграции при старте, состояние проверяется через `GET /api/v1/health`. Внутри Compose приложение подключается к сервису `db`, поэтому `POSTGRES_HOST`, `POSTGRES_PORT` и `DATABASE_URL` из `.env` на него не влияют. Логи пишутся в `logs/`. Приложение в контейнере работает от пользователя с UID 1000, поэтому на Linux этот каталог нужно создать заранее от своего пользователя.

Данные PostgreSQL хранятся в томе `postgres_data` и сохраняются после `docker compose down`. Команда `docker compose down -v` удаляет том вместе с данными. `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` применяются только при первом создании тома: чтобы потом сменить пароль, выполните в базе `ALTER USER ... PASSWORD '...'` и обновите `.env`.

## Миграции

Миграции рассчитаны на PostgreSQL. Команда `uv run alembic upgrade head --sql` выводит SQL миграций без подключения к базе.

Миграция `c41dc2ca3e14` приводит email к нижнему регистру и делает имена пользователей и email уникальными без учета регистра. Если в базе уже есть такие дубликаты, миграция остановится и выведет их список. Миграции выполняются в одной транзакции, поэтому после ошибки база остается в прежнем состоянии.

## Перенос данных из SQLite

До перехода на PostgreSQL данные хранились в `data/db.sqlite3`. Перенести их можно так:

```bash
docker compose up -d db
uv run alembic upgrade head
uv run python -m scripts.transfer_sqlite_to_postgres data/db.sqlite3
```

Скрипт копирует все таблицы одной транзакцией и сдвигает счетчики id, чтобы новые записи не пересекались с перенесенными. Файл SQLite открывается только на чтение. Перенос выполняется, если обе базы на последней миграции, а таблицы в PostgreSQL пустые. При любой ошибке PostgreSQL остается без изменений.

## Тесты

```bash
docker compose up -d db
uv run pytest
```

Тесты создают отдельные базы `<POSTGRES_DB>_test` и `<POSTGRES_DB>_test_empty` на том же сервере и удаляют их после прогона, рабочая база не затрагивается. Пользователю PostgreSQL нужно право создавать базы, у пользователя из контейнера `db` оно есть.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SECRET_KEY` | нет, обязательна | Ключ подписи JWT |
| `ALGORITHM` | `HS256` | Алгоритм подписи: `HS256`, `HS384` или `HS512` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Время жизни access-токена в минутах |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `30` | Время жизни refresh-токена в днях |
| `POSTGRES_USER` | `blog` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | нет, обязательна без `DATABASE_URL` | Пароль пользователя PostgreSQL |
| `POSTGRES_DB` | `blog` | Имя базы данных |
| `POSTGRES_HOST` | `127.0.0.1` | Адрес сервера PostgreSQL |
| `POSTGRES_PORT` | `5432` | Порт сервера PostgreSQL, в Docker Compose также порт на `127.0.0.1` для контейнера `db` |
| `DATABASE_URL` | не задана | Строка подключения вида `postgresql://user:password@host:5432/blog`. Если задана, заменяет переменные `POSTGRES_*` |
| `LOG_FILE` | `logs/app.log` в корне проекта | Файл логов |
| `CORS_ORIGINS` | `*` | Разрешенные источники для CORS через запятую или JSON-списком |
| `AUTH_FAILURES_LIMIT` | `10` | Сколько неудачных попыток входа или конфликтов при регистрации допускается с одного адреса |
| `AUTH_FAILURES_WINDOW_SECONDS` | `300` | Окно в секундах, за которое считаются неудачные попытки |
| `MAX_REQUEST_BODY_BYTES` | `1048576` | Максимальный размер тела запроса в байтах |

## Доступ

- Регистрация (`POST /api/v1/users/`) и чтение опубликованных данных доступны без токена.
- `POST /api/v1/auth/token` выдает пару токенов: короткоживущий access-токен для заголовка `Authorization: Bearer` и refresh-токен. Свой профиль доступен по `/api/v1/users/me`.
- `POST /api/v1/auth/refresh` с телом `{"refresh_token": "..."}` выдает новую пару, а использованный refresh-токен перестает действовать. Если старый refresh-токен предъявят повторно, отзывается вся сессия, к которой он относится.
- `POST /api/v1/auth/logout` с тем же телом отзывает сессию. Уже выданный access-токен действует до окончания своего срока.
- Для смены своего пароля в `PATCH /api/v1/users/me` нужно передать `current_password`. Смена пароля, в том числе администратором, и отключение учетной записи отзывают все токены пользователя.
- После серии неудачных попыток входа или регистрации API отвечает `429` с заголовком `Retry-After`.
- Публикации и комментарии изменяет и удаляет автор или администратор.
- Категории, местоположения и чужие учетные записи изменяет только администратор. Первого администратора назначают в базе, например через `docker compose exec db psql -U blog -d blog`: `UPDATE auth_user SET is_superuser = true WHERE username = '...';`. Последнего администратора нельзя отключить, удалить или лишить прав.
- Неопубликованные категории и местоположения видит только администратор. Неопубликованные и отложенные публикации, а также публикации из скрытых категорий видят их автор и администратор. Публикации идут от новых к старым по дате публикации.
- Список пользователей без прав администратора содержит только активные учетные записи и публичные поля.
- Пользователи, перенесенные из Django, входят со старым паролем. При первом входе хэш пароля переводится на bcrypt.
- Если база недоступна, API отвечает `503`.
